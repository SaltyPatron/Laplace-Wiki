# Engine Performance

Research on what the Intel compiler and OpenMP runtime, concurrent hash tables, batched BLAKE3, PostgreSQL bulk loading, and the VTune and Advisor profilers offer for an ingestion target of about 30 seconds a gigabyte and a fast forward pass, under Laplace's bit-exact determinism.

> [!NOTE]
> Every number on this page comes from the cited source unless it is marked **measured**, in which case it was taken on the Laplace server (Intel Broadwell, AVX2, no AVX-512). Lines marked *inference* are reasoning from the sources, not stated by them. Intel's 2026 option pages render by script, so their quotes come from the search index of the same intel.com URLs or the 2023 to 2025 versions of the same pages; the VTune and Advisor option names were read from the installed tools (`vtune -help`, VTune 2026.4; `advisor --help`, Advisor 2026.0).

## Compiler options under the determinism flags

Laplace needs the same bits from the same input on every machine, so every option is judged first on whether it can change a floating-point result.

| Option | What it does | Determinism |
| --- | --- | --- |
| `-fp-model=precise -fimf-arch-consistency=true -no-fma` | value-safe FP, consistent libm, no fused multiply-add | Intel's stated recipe for consistent results |
| `-O3` | aggressive loop and vector optimization | value-safe FP only under `precise`; integer vectorization gives the same results on every ISA (*inference*) |
| `-march=haswell`, `-xCORE-AVX2` | one named instruction-set floor | safe; it sets which machines can run the binary |
| `-xHost` | the build machine's instruction set | safe but unnamed; another build machine gives another binary |
| `-ax…` | several code paths, one chosen at run time | different machines run different code |
| `-ipo` | interprocedural optimization (LTO) | safe; the FP model still applies |
| PGO | inlining, layout, unrolling from a profile | safe; it does not change FP semantics |

- The icx default FP model is `-fp-model=fast`. Intel's porting guide says "using -fp-model=precise -fimf-arch-consistency=true -no-fma as a workaround helps achieve" consistency. [Porting guide for ICC users to DPC++ or ICX](https://www.intel.com/content/www/us/en/developer/articles/guide/porting-guide-for-icc-users-to-dpcpp-or-icx.html)
- `-no-fma` is not redundant with `precise`. LLVM's `-ffp-model=precise` "Disables optimizations that are not value-safe ... although FP contraction (FMA) is enabled" (`-ffp-contract=on`). [Clang User's Manual](https://clang.llvm.org/docs/UsersManual.html)
- Intel's consistency article lists `-fp-model precise` with `-fp-model source` or `consistent`, `-fimf-arch-consistency=true` for processors of one architecture, and `-no-fma` for machines with and without FMA. [Consistency of floating-point results](https://www.intel.com/content/www/us/en/developer/articles/technical/consistency-of-floating-point-results-using-the-intel-compiler.html)
- `-fimf-arch-consistency` applies to the math library functions only. [fimf-arch-consistency](https://www.intel.com/content/www/us/en/docs/dpcpp-cpp-compiler/developer-guide-reference/2024-1/fimf-arch-consistency-qimf-arch-consistency.html)
- `-x` and `-march` name the instruction set the code may use; for an AVX2 floor the names are `-xCORE-AVX2`, `-march=haswell`, or `-march=x86-64-v3`. [x, Qx](https://www.intel.com/content/www/us/en/docs/dpcpp-cpp-compiler/developer-guide-reference/2023-1/x-qx.html)
- `-ax` generates "multiple, feature-specific auto-dispatch code paths for Intel processors if there is a performance benefit"; one is chosen at run time and non-Intel processors run the baseline. [ax, Qax](https://www.intel.com/content/www/us/en/docs/dpcpp-cpp-compiler/developer-guide-reference/2023-1/ax-qax.html)
- "LLVM uses Link Time Optimization (LTO) technology, which is termed as 'Interprocedural Optimization' (IPO) in ICC"; `-ipo` sets `-flto`. [ipo, Qipo](https://www.intel.com/content/www/us/en/docs/dpcpp-cpp-compiler/developer-guide-reference/2024-2/ipo-qipo.html)
- Instrumented PGO is `-fprofile-instr-generate`, a training run, `llvm-profdata merge`, then `-fprofile-instr-use`. Hardware sampling PGO (`-fprofile-sample-generate`, `-fprofile-sample-use`) is experimental. [Hardware profile-guided optimization](https://www.intel.com/content/www/us/en/docs/dpcpp-cpp-compiler/developer-guide-reference/2024-2/hardware-profile-guided-optimization.html)
- `-qopt-report[=0..3]` writes YAML optimization reports, level 2 by default and 3 for full loop detail; 2026.0 adds `-qopt-report-routine=name[,name]`. [qopt-report](https://www.intel.com/content/www/us/en/docs/dpcpp-cpp-compiler/developer-guide-reference/2023-2/qopt-report-qopt-report.html), [oneAPI DPC++/C++ 2026 release notes](https://www.intel.com/content/www/us/en/developer/articles/release-notes/oneapi-dpcpp/2026.html), [Compiler optimization report news 2025](https://www.intel.com/content/www/us/en/developer/articles/technical/compiler-optimization-report-news-2025.html)
- `-fiopenmp` links the Intel OpenMP runtime (libiomp5); icx's `-fopenmp` uses the open-source runtime and is documented for compatibility testing, not performance; `-qopenmp` is the older spelling of `-fiopenmp`. [Porting guide](https://www.intel.com/content/www/us/en/developer/articles/guide/porting-guide-for-icc-users-to-dpcpp-or-icx.html)
- **Measured:** the build defined in `Laplace-Native/cmake/LaplaceFlags.cmake` compiles the shared code with `-fp-model=precise -ffp-contract=off -fno-fast-math -march=x86-64-v2` and the dispatched kernels with `-march=x86-64-v3 -mavxvnni` or `-march=x86-64-v4 -mavx512vnni`. `-ffp-contract=off` is the LLVM spelling of `-no-fma`.

## OpenMP tasks and the Intel runtime

- With no `grainsize` or `num_tasks`, `__kmp_taskloop` comments "let's try to schedule (team_size*10) tasks": 120 tasks a taskloop on 12 threads, split recursively past `KMP_TASKLOOP_MIN_TASKS`. [kmp_tasking.cpp](https://raw.githubusercontent.com/llvm/llvm-project/main/openmp/runtime/src/kmp_tasking.cpp)
- A `taskloop` runs "as if it was enclosed in a taskgroup construct" unless `nogroup` is given, which is not allowed with a reduction. `grainsize(g)` gives each task g to 2g iterations, `grainsize(strict: g)` exactly g, and `num_tasks(n)` min(n, iterations) tasks. [OpenMP 5.1, taskloop](https://www.openmp.org/spec-html/5.1/openmpsu55.html)
- `nowait` removes a construct's implicit barrier. [OpenMP 5.2, nowait](https://www.openmp.org/spec-html/5.2/openmpse94.html) `taskwait` waits for a task's children; `taskgroup` waits for all descendants. [OpenMP 5.2, synchronization](https://www.openmp.org/spec-html/5.2/openmpse93.html)

| Setting | Default | Meaning |
| --- | --- | --- |
| `KMP_BLOCKTIME` | 200 ms | how long an idle thread spins before it sleeps |
| `OMP_WAIT_POLICY` | passive, with the `KMP_BLOCKTIME` spin | active spins, passive sleeps |
| `KMP_LIBRARY` | throughput | turnaround keeps threads spinning |
| `KMP_AFFINITY` | `granularity=core,none` (unbound) | overrides `OMP_PROC_BIND` |
| `OMP_PROC_BIND` | false | close, spread, or master binding |
| `OMP_PLACES` | none | threads, cores, sockets, or ll_caches |
| `KMP_HOT_TEAMS_MAX_LEVEL` | 1 | nested teams are created each time they are entered |

Sources: [LLVM OpenMP runtimes](https://openmp.llvm.org/design/Runtimes.html), [OMP_WAIT_POLICY and KMP_BLOCKTIME](https://community.intel.com/t5/Intel-C-Compiler/OMP-WAIT-POLICY-and-KMP-BLOCKTIME/td-p/1066367).

- VTune divides OpenMP overhead into imbalance, lock contention, creation, scheduling, atomics, and reduction. Its remedies are dynamic scheduling for imbalance, larger chunks for scheduling overhead, no synchronization inside the construct (reductions, thread-local storage, cheaper atomics) for lock contention, and more parallel work for serial time. [OpenMP code analysis method](https://www.intel.com/content/www/us/en/docs/vtune-profiler/cookbook/2023-0/openmp-code-analysis-method.html), [OpenMP imbalance and scheduling overhead](https://www.intel.com/content/www/us/en/docs/vtune-profiler/cookbook/2023-2/openmp-imbalance-and-scheduling-overhead.html)
- Intel's Guide for Developing Multithreaded Applications covers granularity (1-3), load balance (1-4), heap contention (3-1), thread-local storage to reduce synchronization (3-2), and false sharing (3-4). [Guide for developing multithreaded applications](https://www.intel.com/content/www/us/en/developer/articles/guide/guide-for-developing-multithreaded-applications.html)
- Per-thread partial results merged in a fixed order (by chunk index, never by thread ID or completion order) keep the output independent of scheduling. *Inference.*

## Concurrent tables for 128-bit IDs

A composition's ID is 16 bytes, and ingestion asks, for every node it builds, whether that ID was already seen. Hot IDs (common words, common subtrees) repeat constantly, so the table's behaviour under skew decides throughput.

- Preshing's "World's Simplest Lock-Free Hash Table" is a flat array with linear probing where key 0 means empty. An insert reads, then uses compare-and-swap only to claim an empty slot; a lookup is plain loads with no compare-and-swap and no lock, so a hit never writes. It has a fixed power-of-two size, no deletion, and works to about 80% full. Replacing a contended lock with it took a game from 4 to 10 frames a second. [The World's Simplest Lock-Free Hash Table](https://preshing.com/20130605/the-worlds-simplest-lock-free-hash-table/)
- Maier, Sanders, and Dementiev measured "folklore" lock-free linear probing over 128-bit cells, with `cmpxchg16b` on key and value, as considerably faster than similarly restricted tables and about an order of magnitude faster than general ones (up to four orders in extreme cases). Under Zipf skew s = 1.25, finds reached a 23.2× speedup because hot keys stay cached and are only read; inserts and updates of one hot key begin to suffer between s = 0.85 and 0.95. Lock-based TBB tables got slower with more cores on 2 sockets and 48 threads. They size tables at 2n to 4n slots and grow at about 60% by doubling with parallel cluster-wise migration. [Concurrent Hash Tables: Fast and General?(!)](https://arxiv.org/abs/1601.04017), [TOPC 2019](https://dl.acm.org/doi/10.1145/3309206)
- Folly's AtomicHashMap and AtomicHashArray are fixed-size open addressing. An insert swaps the key from empty to a reserved locked key, writes the value, then publishes the real key; find is wait-free. Folly claims 2× to 5× over `tbb::concurrent_hash_map`; it needs reserved empty, locked, and erased keys. [AtomicHashMap](https://github.com/facebook/folly/blob/main/folly/docs/AtomicHashMap.md)
- Shun and Blelloch's phase-concurrent linear probing (concurrent inserts and finds in separate phases) ran 1.3× to 4.1× faster than hopscotch and chained tables and up to 52× faster than sequential on 40 cores. [Phase-concurrent hash tables, SPAA 2014](https://dl.acm.org/doi/10.1145/2612669.2612687)
- `cmpxchg16b` needs 16-byte alignment. On AVX processors an aligned 16-byte `VMOVDQA` load or store is atomic, and GCC's libatomic uses it; older paths implement the load as `cmpxchg16b`, a write that brings cache-line contention back on hits. The alternative is to swap a 64-bit word holding a hash tag and a record index, then confirm the full 128-bit ID against the record array. [rigtorp, isatomic](https://rigtorp.se/isatomic/), [GCC libatomic patch discussion](https://patchwork.ozlabs.org/comment/3001586/)
- Boost's `concurrent_flat_map` probes and SIMD-matches without a lock and locks only to confirm; against TBB and gtl under Zipf 0.01, 0.5, and 0.99 it generally won, and gtl's 256 fixed shards did worst under high skew. [Inside boost::concurrent_flat_map](http://bannalia.blogspot.com/2023/07/inside-boostconcurrentflatmap.html)
- oneTBB's `concurrent_hash_map` takes a per-bucket spin reader-writer lock, and even a const accessor's reader lock is an atomic write to the hot cache line, so a hot key serializes much like a mutex. [concurrent_hash_map](https://uxlfoundation.github.io/oneTBB/main/tbb_userguide/concurrent_hash_map.html) Its `concurrent_unordered_set` is split-ordered lists with one allocation a node. [Split-ordered lists](https://www.cs.tau.ac.il/~afek/SplitOrderListHashSS03.pdf) Both are C++ templates, reachable from C only through `extern "C"` wrappers.
- The oneTBB scalable allocator has a C interface (`scalable_malloc`, `scalable_free`, `scalable_realloc`, `scalable_aligned_malloc`, and the rest from `oneapi/tbb/scalable_allocator.h`, linked with `-ltbbmalloc`) and a whole-process replacement (`LD_PRELOAD=libtbbmalloc_proxy.so` or `-ltbbmalloc_proxy`). It removes contention inside malloc; it does not help a realloc made while a lock is held. [C interface to scalable allocator](https://oneapi-spec.uxlfoundation.org/specifications/oneapi/latest/elements/onetbb/source/memory_allocation/c_interface_to_scalable_allocator), [Dynamic memory interface replacement](https://uxlfoundation.github.io/oneTBB/main/tbb_userguide/Linux_C_Dynamic_Memory_Interface_Replacement.html)
- HyPer's morsel-driven aggregation lets per-thread small fixed tables absorb heavy hitters and spill into hash partitions that one thread each merges. [Morsel-driven parallelism](https://db.in.tum.de/~leis/papers/morsels.pdf) DuckDB pre-aggregates per thread and merges radix partitions. [Kuiper, Boncz, Mühleisen, ICDE 2024](https://duckdb.org/pdf/ICDE2024-kuiper-boncz-muehleisen-out-of-core.pdf) "Global Hash Tables Strike Back!" finds a purpose-built global concurrent table matching or beating partitioning for GROUP BY across group counts, skew, and threads, and a general-purpose one not. [arXiv 2505.04153](https://arxiv.org/abs/2505.04153)
- **Measured:** the engine's node table was 256 mutex-guarded shards, the gtl design; a thread-local front cache of 32,768 IDs in `compose` (`Laplace-Engine/src/table.c`) now answers repeats before any shard lock.

## BLAKE3 for many small inputs

A Laplace node's ID is BLAKE3 over its children's 16-byte IDs, so a node of n children hashes 16n bytes: 32 bytes for a pair, rarely more than a kilobyte. Ingestion hashes hundreds of millions of these.

- Below one 1 KiB chunk, `blake3_hasher_update` buffers bytes and compresses each 64-byte block in turn, each block's chaining value feeding the next. `blake3_hash_many` is called only for whole chunks. A 16n-byte node costs ⌈16n/64⌉ serial compressions with nothing to spread across lanes. [blake3.c](https://raw.githubusercontent.com/BLAKE3-team/BLAKE3/master/c/blake3.c)
- There is no AVX2 single-block compress: `blake3_compress_in_place` dispatches to AVX-512VL, else SSE4.1, else SSE2. On a processor without AVX-512 every single hash runs the 4-wide SSE4.1 compress; AVX2 is used only by `hash_many`, 8 inputs at once. [blake3_dispatch.c](https://raw.githubusercontent.com/BLAKE3-team/BLAKE3/master/c/blake3_dispatch.c)
- `blake3_hasher` is about 1.9 KB (key, chunk state with a 64-byte buffer, a stack of 55 chaining values); for inputs of one to five compressions the per-call setup and finalization are a real share of the cost. [blake3.h](https://raw.githubusercontent.com/BLAKE3-team/BLAKE3/master/c/blake3.h) The TBB-parallel update is slower than the plain one below 128 KiB on x86-64. [BLAKE3 C README](https://raw.githubusercontent.com/BLAKE3-team/BLAKE3/master/c/README.md)
- Short-input BLAKE3 is slow in practice: one bindings-level measurement found BLAKE2s faster below about 80 bytes. [Short-input hashing](https://jszym.com/blog/short_input_hash/) Firedancer found BLAKE3 slower than batched SHA-256 up to about 4 KB because "libraries for multi-message (batch) hashing exist for SHA-256, but not for BLAKE3". [Solana forum](https://forum.solana.com/t/blake3-slower-than-sha-256-for-small-inputs/829)
- The internal `blake3_hash_many(inputs, num_inputs, blocks, key, counter, increment_counter, flags, flags_start, flags_end, out)` has AVX2, SSE4.1, SSE2, and portable variants and is not public API; on x86 the widest degree is 16. [blake3_impl.h](https://raw.githubusercontent.com/BLAKE3-team/BLAKE3/master/c/blake3_impl.h) The AVX2 `hash8` transposes 8 inputs into lanes and runs the rounds 8 wide with every block length fixed at 64, `flags_start` on the first block and `flags_end` on the last, every lane the same block count. [blake3_avx2.c](https://raw.githubusercontent.com/BLAKE3-team/BLAKE3/master/c/blake3_avx2.c)
- Every input to `hash_many` must be a whole number of 64-byte blocks. A partial final block hashes with its true length inside the compression, so zero padding gives a different hash; the Rust equivalent silently ignored a partial last block in release builds, producing collisions, and is documented as "undocumented and unstable, for benchmarks only". [BLAKE3 issue 590](https://github.com/BLAKE3-team/BLAKE3/issues/590)
- The standard digest through the kernel is counter 0, no counter increment, flags 0, `CHUNK_START` on the first block and `CHUNK_END | ROOT` on the last; the 32-byte chaining value is the digest. Plonky3 sends the whole-block prefix through `hash_many` and gives the short final block "a scalar compression per message" because "the vectorized hash_many always sets [block_len] to 64". [Plonky3 PR 2151](https://github.com/Plonky3/Plonky3/pull/2151) Iroh's batch hashing requires equal sizes that are multiples of 64 and a count that is a multiple of the SIMD degree. [Hashing multiple blobs with BLAKE3](https://www.iroh.computer/blog/hashing-multiple-blobs-with-BLAKE3)
- An upstream request for an API to SIMD-hash many equal-length values, such as 2¹⁶ 32-byte Merkle inputs, is unresolved. [BLAKE3 issue 478](https://github.com/BLAKE3-team/BLAKE3/issues/478) Commonware wrote AVX-512 ×16, AVX2 ×8, and NEON ×4 kernels that run "equal-length messages... in lockstep at any length". [commonware PR 4982](https://github.com/commonwarexyz/monorepo/pull/4982)
- Intel ships no BLAKE3: IPP Cryptography hashes SHA-1, SHA-2, SHA-3, SHAKE, MD5, and SM3 [IPP hash functions](https://www.intel.com/content/www/us/en/docs/ipp-crypto/developer-guide-reference/2021-12/hashinit.html); crypto_mb covers RSA, ECDSA, ECDH, X25519, Ed25519, SM2, SM3, and SM4 [multi-buffer functions](https://www.intel.com/content/www/us/en/docs/ipp-crypto/developer-guide-reference/2021-12/multi-buffer-cryptography-functions.html); isa-l_crypto covers SHA1, SHA256, SHA512, MD5, and SM3 [isa-l_crypto](https://github.com/intel/isa-l_crypto).

| --- | --- | --- | --- | --- |
| Plonky3, 4096 × 64 B | Zen 5, AVX-512 ×16 | 752 MiB/s | 11.5 GiB/s | 15.7× |
| Plonky3, 4096 × 256 B | Zen 5, AVX-512 ×16 | 929 MiB/s | 13.2 GiB/s | 14.5× |

## PostgreSQL bulk loading

- `COPY` beats `INSERT`. The fastest load of a fresh table is create, `COPY`, then build indexes, with a large `max_wal_size`, `wal_level=minimal`, `archive_mode=off`, and `max_wal_senders=0`: "COPY is fastest when used within the same transaction as an earlier CREATE TABLE or TRUNCATE command. In such cases no WAL needs to be written." Run `ANALYZE` afterwards. [Populating a database](https://www.postgresql.org/docs/18/populate.html)
- Binary format "is somewhat faster than the text and CSV formats". `COPY FREEZE` needs the table created or truncated in the current subtransaction, with no open cursors or older snapshots, and "It is currently not possible to perform a COPY FREEZE on a partitioned table", so it must target each leaf partition. [COPY](https://www.postgresql.org/docs/18/sql-copy.html)
- Cybertec loaded 500 million rows in 627 s with plain `COPY` and 304 s with `COPY FREEZE` after `TRUNCATE` under `wal_level=minimal`, and later reads skipped the hint-bit and vacuum pass. [Loading data in the most efficient way](https://www.cybertec-postgresql.com/en/loading-data-in-the-most-efficient-way/) In pgbench on PostgreSQL 14, `COPY FREEZE` cut initialization from 16.2 s to 14.3 s and the following vacuum from 2.13 s to 0.25 s. [Speeding up pgbench using COPY FREEZE](https://pgsqlpgpool.blogspot.com/2021/03/speeding-up-pgbench-using-copy-freeze.html)
- Under `wal_level=minimal`, `CREATE TABLE`, `TRUNCATE`, `REINDEX`, `CLUSTER`, and similar write no row WAL; at commit, relations of at least `wal_skip_threshold` (2 MB) are fsynced instead. There is no point-in-time recovery and `max_wal_senders` must be 0. `synchronous_commit=off` can lose about three `wal_writer_delay` intervals of commits in a crash but never consistency. `wal_compression` takes pglz, lz4, or zstd. The defaults are `max_wal_size` 1 GB, `checkpoint_timeout` 5 min, and `checkpoint_completion_target` 0.9, and every checkpoint brings fresh full-page writes. [Write-ahead log](https://www.postgresql.org/docs/18/runtime-config-wal.html)
- Unlogged tables write no WAL and are truncated after a crash, and their indexes are unlogged too; `SET LOGGED` and `SET UNLOGGED` "is not supported for partitioned tables". [CREATE TABLE](https://www.postgresql.org/docs/18/sql-createtable.html), [ALTER TABLE](https://www.postgresql.org/docs/18/sql-altertable.html)
- PostgreSQL 16 made relation extension cheaper, which helps concurrent `COPY` into one relation. [PostgreSQL 16 release notes](https://www.postgresql.org/docs/16/release-16.html) Parallel `COPY` over several connections into different partitions is the usual way to scale; no primary-source per-partition benchmark was found. [Testing Postgres ingest](https://www.tigerdata.com/learn/testing-postgres-ingest-insert-vs-batch-insert-vs-copy)
- For GIN, "for bulk insertions into a table it is advisable to drop the GIN index and recreate it after finishing bulk insertion." With `fastupdate`, new entries go to an unsorted pending list that is merged by vacuum, autoanalyze, `gin_clean_pending_list()`, or when it passes `gin_pending_list_limit` (4 MB by default, per index); the insert that overflows it pays the whole merge, and every search scans the pending list. "Build time for a GIN index is very sensitive to the maintenance_work_mem setting." [GIN](https://www.postgresql.org/docs/18/gin.html)
- PostgreSQL 18 builds GIN in parallel; parallel `CREATE INDEX` covers B-tree, GIN, and BRIN, not GiST. `maintenance_work_mem` is the whole build's budget, at least 32 MB a worker plus the leader; `max_parallel_maintenance_workers` defaults to 2, and a table's `parallel_workers` overrides it. [CREATE INDEX](https://www.postgresql.org/docs/18/sql-createindex.html), [Resource consumption](https://www.postgresql.org/docs/18/runtime-config-resource.html), [PostgreSQL 18 release notes](https://www.postgresql.org/docs/18/release-18.html)
- A sorted GiST build is 2× to 5× faster, but PostGIS ships sort support only for 2D (`geometry_gist_sortsupport_2d`), and the sorted index can query up to about 30% slower. No n-D sort support was found, so `gist_geometry_ops_nd` builds by insertion (*inference*). [PostGIS 3.2](https://www.crunchydata.com/blog/postgis-3.2-new-and-improved)
- A heap-only-tuple (HOT) update needs no indexed column changed and free space on the page. `fillfactor` defaults to 100, and "in heavily updated tables smaller fillfactors are appropriate". [HOT](https://www.postgresql.org/docs/18/storage-hot.html), [CREATE TABLE](https://www.postgresql.org/docs/18/sql-createtable.html)
- `UPDATE ... FROM unnest(arrays)` took 41 ms against 41 ms for a binary-`COPY` temporary table plus `UPDATE ... FROM` at 10,000 rows, and 92 against 93 ms at 25,000; per-row updates took 2,414 ms at 10,000. The temporary table costs a fixed 6 to 8 ms a statement. [Optimizing bulk database updates](https://milanjovanovic.tech/blog/optimizing-bulk-database-updates-in-dotnet)
- PostgreSQL 18 adds asynchronous I/O: `io_method` worker (the default), io_uring, or sync; `io_workers` 3; `effective_io_concurrency` and `maintenance_io_concurrency` 16. It covers reads only (sequential scans, bitmap heap scans, vacuum); writes, checkpoints, and WAL flushes stay synchronous. A cold-cache scan took 15.8 s on 17, 10 s on 18 with workers, and 5.7 s with io_uring. [Resource consumption](https://www.postgresql.org/docs/18/runtime-config-resource.html), [pganalyze, Postgres 18 async I/O](https://pganalyze.com/blog/postgres-18-async-io) PostgreSQL 18 also adds eager page freezing in vacuum and WAL I/O in `pg_stat_io`. [PostgreSQL 18 release notes](https://www.postgresql.org/docs/18/release-18.html)

## Profiling with VTune and Advisor

The VTune drivers are loaded on the server (**measured:** `lsmod` shows sep5, vtsspp, and pax), so hardware event sampling runs. Without them VTune falls back to driverless perf-based sampling, which needs `perf_event_paranoid` at 0 or below. [SEP driver](https://www.intel.com/content/www/us/en/docs/vtune-profiler/user-guide/2024-2/sep-driver.html)

| Analysis | Command (`vtune -collect … -r R -- laplace …`) | Answers |
| --- | --- | --- |
| Hotspots, user mode | `hotspots -knob sampling-mode=sw -knob enable-stack-collection=true` | where time goes, fixed 10 ms samples |
| Hotspots, hardware | `hotspots -knob sampling-mode=hw -knob sampling-interval=1 -knob enable-stack-collection=true -knob stack-size=0` | the same at 0.01 to 1000 ms intervals, unlimited stacks |
| Threading | `threading -knob sampling-and-waits=hw -knob enable-stack-collection=true` | waits, locks, and their call stacks |

## Applied to the engine

What the sources above lead to, in the order the engine's work runs:

- **Build.** icx at `-O3` with a named AVX2 floor, `-fiopenmp`, and `-ipo`, keeping `-fp-model=precise -fimf-arch-consistency=true -no-fma`; then instrumented PGO trained on a real ingest. No `-ax` and no `-xHost`. `-qopt-report=3 -qopt-report-routine=` for the hashing and table routines, and `-parallel-source-info=2` when profiling.
- **Threads.** Every `taskloop` gets an explicit coarse `grainsize(strict: N)`; there is one level of tasks, or `nogroup` under a single outer `taskgroup`, so no task waits on its own children's barrier. Per-thread structures are padded to cache lines and merged in chunk order. `OMP_PLACES=cores OMP_PROC_BIND=close` is set for ingestion.
- **Node table.** One pre-sized lock-free linear-probing table, 2× to 4× the expected unique IDs and at most 60% full, replaces the 256 shards: a hit is plain loads; a miss claims a 64-bit tag and record index by compare-and-swap and is confirmed against the 16-byte ID in one reserved record array filled by per-thread chunks, so nothing reallocates under a lock. The thread-local front cache stays in front of it, and tbbmalloc takes the remaining malloc traffic.
- **Hashing.** The public `blake3_hasher` stays the bit-exact reference. Node hashes are batched by block count: a node of n children is ⌊n/4⌋ whole blocks plus a partial block when n mod 4 ≠ 0. An own 8-lane AVX2 compress built from `blake3_avx2.c`'s round function and transpose, with block length and flags per lane, runs 8 nodes in lockstep (counter 0, `CHUNK_START` first, `CHUNK_END | ROOT` last), and the first 16 bytes of each output are the ID. The internal `blake3_hash_many` is not used: it is not public, its block length is fixed at 64, and every two-child node is a 32-byte partial block. Every lane is checked against `blake3_hasher` at every boundary length from 32 to 1,024 bytes.
- **Loading.** Full loads go per leaf partition in parallel, one connection each, `TRUNCATE` or create plus binary `COPY FREEZE` in one transaction under `wal_level=minimal`, with indexes built afterwards under a large `maintenance_work_mem` and parallel workers (GIN in parallel; GiST by building partitions concurrently). Incremental loads run with `fastupdate` off or one `gin_clean_pending_list` per load. Consensus gets `fillfactor` 70 to 80 with no index on the columns Glicko-2 changes, so rating updates stay HOT. Bulk sessions run with `synchronous_commit=off`, a large `max_wal_size`, a long `checkpoint_timeout`, and `wal_compression` lz4 or zstd; io_uring serves the read-heavy phases.
- **Measuring.** VTune threading with hardware waits first (lock and barrier time), then hardware hotspots with stacks, memory access for the node table, and the HPC analysis for OpenMP imbalance; Advisor's integer roofline for the hashing kernel.

## Measured on the engine

Every number here is **measured** with `laplace ingest --no-load` on the Laplace server (6 cores, 12 threads, Broadwell, AVX2), decomposition only, with no other ingest running unless noted. Every change was checked against what it replaced: the same compositions, the same attestations, and every file recomposed byte for byte; for the reading changes, the claims listing (`laplace ingest --claims`) identical line for line, in order, to the whole file read on one thread.

VTune 2026.4 does not recognize the Broadwell processor for any collection, hardware or user-mode, so the profiles below come from Linux `perf` with last-branch-record call stacks (`perf record --call-graph lbr`).

| Change | Source | Before | After |
| --- | --- | --- | --- |
| One lock-free node table in place of 256 locked shards | FrameNet, 854 MB | 66.4 s | 55.2 s |
| A batch's files begun longest first | FrameNet | 55 s | 44.8 s |
| A long file of records parsed on every core as one tree (`split`, s_grammar_split) | Open Multilingual Wordnet, 597 MB, side by side | 158 s | 56 s |
| The same, for Unicode's database (whole file against split) | Unicode, 239 MB | 235 s | 51 s |
| A wide part's parts read and composed on every core, in order | Unicode | 51 s | 32 s |
| oneTBB's scalable allocator for the whole program | Unicode | 32 s | 24.9 s |
| The same allocator, at the same load, on the build before it | FrameNet | 85.7 s | 61.6 s |

What the profiles showed, and what was done about each:

- **The node table was not the bottleneck.** After the lock-free table, `compose` and its table were about 2% of FrameNet's cycles.
- **Idle threads were.** On FrameNet about 20% of cycles, and on the Open Multilingual Wordnet about 45%, were the Intel OpenMP runtime spinning for work (`__kmp_execute_tasks`, `kmp_flag_64::wait`). The cause was one long file decomposed on one core while the others waited: FrameNet's 25 MB `lemma_to_wordformR1.7.xml` was begun near the end of the batch, and the Open Multilingual Wordnet's 115 MB `omw-en.xml` was parsed and read on one core. Beginning the longest files first, and parsing a long file's records on every core, took that waiting away.
- **A file of records parted for parsing must still be read as one tree.** The engine's `split` parsed each part as a tree of its own, and a recipe's keys resolve within the tree being read, so a key in one part (a synset's members) did not resolve in another. The parts are now parsed on every core and each record is grafted into the innermost group around it in the file, which gives the tree the whole file's parse gives.
- **The reading after the parse was serial.** Unicode's reading took 68 s on one thread after a 28 s parse. The parts of a part holding 4,096 or more parts are now read in runs on every core, each run into a sink of its own, the sinks kept in the file's order; the things composed of the tree are shared between threads, each the same whoever composes it.
- **tree-sitter's parse is now the largest cost**, and inside it `malloc`: a thread-local front cache, the lock-free table and oneTBB's allocator leave the grammar's own work (`ts_parser_parse`, `ts_parser__reduce`, the stack, and the XML scanner's per-token state, which `tree_sitter_xml_external_scanner_deserialize` rebuilds with one allocation per open tag) as what remains.
- **A node's tier is the lowest it is composed at.** The same ID composed at two tiers (`[a,n]` as a repeated block inside "banana" at tier 1, and as the word "an" at tier 2) kept whichever thread inserted it first, so two runs of the same input could differ. It is now recorded at the lowest tier it is composed at in a batch. Across batches and runs the same ID can still be composed at a tier other than the one it was recorded at, and the deduplication probe looks only in the partition of the tier it is composed at.
- **A node's hash without the hasher.** A node's input is its children's IDs, 16 bytes each, and nearly always fits one 1,024-byte chunk. `lp_hash16` (Laplace-Native) chains the chunk's 64-byte blocks from BLAKE3's IV with `blake3_compress_in_place` and finishes the last block with `CHUNK_END | ROOT` at its own length and counter 0 through `blake3_compress_xof`. That is the standard digest, without setting up the 1.9 KB hasher and without one 16-byte update per child. **Measured:** every length from 0 to 2,048 bytes, 200 random inputs each (409,800 inputs), gave the same 16 bytes as `blake3_hasher`. On ConceptNet, hashing (`compose`, `lp_ref_compose`, BLAKE3's compress, update and finalize) had been about 18% of decomposition's cycles.
- **Writing is now the cost, not reading.** The first source recorded in full with these changes, Universal Dependencies (3.4 GB), took 1,615.5 s: decomposition 122.6 s (29.2 MB/s), deduplication 36.0 s, the entities and paths COPY 249.6 s (13,231,450 rows each, 106,007 rows/s), the GIN pending lists merged 45.6 s, and the witnesses, ledger and standings 1,137.1 s (105,443,262 attestations; 19,198,000 standings new and 3,993,380 updated). That last phase writes on one connection, in one transaction, because what a batch attests and its files' trunks are recorded together or not at all.
