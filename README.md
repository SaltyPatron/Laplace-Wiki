# Laplace-Wiki

<p align="center"><img src="assets/laplace-logo.webp" alt="Laplace" width="640"></p>

This repository is the Laplace documentation. It explains how everything at every level works.

Read it online at <https://saltypatron.github.io/Laplace-Wiki/>.

The page tree below covers the Wiki pages. [Repository documentation](Repositories/README.md) holds the relocated repository trees.

## Pages

- [Repository documentation](Repositories/README.md) — Documentation relocated from the implementation repositories is grouped here by its original repository and path.
- [Architecture](Architecture.md) — Laplace is native C, with SQL and C# as orchestration.
- [Engineering](Engineering/README.md) — the engineering standard and the architecture boundaries bind every implementation choice in every active repository.
  - [Laplace engineering standards](Engineering/Standards.md) — these standards keep implementation choices subordinate to the complete invention.
  - [Architecture boundaries](Engineering/Boundaries.md) — architecture boundaries state which layer owns which law: the native engine owns every semantic operation, and SQL and C# orchestrate generated typed bindings to it.
- [Sequence](Sequence/README.md) — Laplace is built in one order, and each stage is impossible without the one before it: Unicode onto the S³, tier 0, the registries and perf-caches, the store, sources through recipes into content, attestations, consensus, indexes, the web, authority, the compute envelope, the firmware, the forward program, sessions, and only then a user, whose consequences feed the learning loop that models, export, code, chess, and games all run on.
  - [1. Unicode](Sequence/Unicode.md) — the first operations fix one Unicode version and read every file tier 0 and segmentation are built from.
  - [2. Toolchain](Sequence/Toolchain.md) — the machine, the drives, the source root, and every dependency built from source with one compiler and the flags that give the same bits everywhere.
  - [3. Builds](Sequence/Builds.md) — PostgreSQL, Laplace-Native, Laplace-postgres, and Laplace-Engine are built in that order, each linking the one before it, and two compilers must agree on every golden value.
  - [4. Projection](Sequence/Projection.md) — every codepoint gets its point on the S³: the DUCET order, the Super-Fibonacci points, the Hilbert order, and rank r to the r-th point.
  - [5. Tier 0](Sequence/Tier-0.md) — every codepoint's ID, fixed-point coordinate, Hilbert value, and flags are written once into a fingerprinted file that the client and the database map.
  - [6. Registries](Sequence/Registries.md) — before any source is admitted, the 64-bit mask banks, highway vocabularies, trust classes, model operator templates, and firmware policy kinds are enumerated as governed, append-only perf-caches: every member is a content-derived entity (`noun` is `[n,o,u,n]`), its stable bit or slot is only an acceleration index over it, any content entity may serve as a claim predicate without registration, and no registry is a table of made-up IDs.
  - [7. Perfcaches](Sequence/Perfcaches.md) — above tier 0, every deterministic reusable layer that earns it is emitted as a fingerprinted, rebuildable, memory-mapped ROM whose dependencies follow composition, from number roots and vocabularies up to pixels, positions, and images.
  - [8. Database](Sequence/Database.md) — the server is tuned, the extensions are created, the database is told its tier 0, and the partitioned content and semantics schema is made.
  - [9. Sources](Sequence/Sources.md) — a source is admitted as one release, staged and qualified together, with every artifact given a disposition and none silently skipped; its identity is its trunk, `[source record, its files' trunks]`, so a release is its files and no name, version, or recipe is ever part of an ID.
  - [10. Recipes](Sequence/Recipes.md) — one generic decomposer turns bytes into structure, and one semantic recipe per curated source says what each recovered field becomes: content, occurrence, reference, provenance, testimony, calculation, packaging, or an explicit unresolved obligation.
  - [11. Content](Sequence/Content.md) — content runs one ordered ingest spine: unpack, records, working-set deduplication, accumulation, bulk tier descent, apply by COPY, fold completion, and a receipt, with the DAG built and hashed on the client and deduplicated trunk to leaf against what is already recorded.
  - [12. Attestations](Sequence/Attestations.md) — curated corpora are recorded as witnesses and claims, n-ary compositions of content IDs attached at the tier the source asserts them, with enumerated values as mask bits, sets as collections, and calculations marked as such.
  - [13. Consensus](Sequence/Consensus.md) — each attestation, one per strand and witness, is played as one Glicko-2 game series at the witness's trust, as it arrives: its games, how many times the witness asserts the strand, solved on the client as one update, with its score; witnesses play first in, first out, with no global or delayed folds.
  - [14. Indexes](Sequence/Indexes.md) — after a bulk load the indexes are built, the planner is told what the columns really are, and the install is measured and checked against itself.
  - [15. Web](Sequence/Web.md) — with standings on every claim, a pull reads a standing as a confidence and a cost, and hops and fans out over the web at O(log N) + O(K) a step.
  - [16. Authority](Sequence/Authority.md) — knowledge, authority, and compute are three independent axes: what exists in the one world, what a principal may do with which part of it, and how much work one operation may spend, resolved as an explicit effective scope before any cognition couples.
  - [17. Envelope](Sequence/Envelope.md) — every operation runs under an explicit compute envelope: hops, fanout, frontier, candidates, providers, trajectory expansion, calculation, memory, I/O, concurrency, and output, planned before execution, reserved, enforced under counters, receipted, and reconciled.
  - [18. Firmware](Sequence/Firmware.md) — the decisions a pull makes are written as a versioned, content-addressed program over the instruction set, one firmware image per human being or task, loaded once per pass, named in every receipt, rated by its consequences, and kept out of the records.
  - [19. Pull](Sequence/Pull.md) — a lookup computes the ID on the client and hits the indexes, and every operator the forward program can call, containment, gap, continuation, shape, relation read, and batch realization, is an indexed set access followed by one native operation.
  - [20. Forward](Sequence/Forward.md) — one stateful, typed program answers every request: RESOLVE, COUPLE, ORIENT, ROUTE, SCAN, COMPOSE, PROPOSE, STEER, SELECT, REALIZE, WITNESS, each emitted constituent changing the state before the next, over one shared witnessed substrate, under the firmware, the authority, and the envelope.
  - [21. Sessions](Sequence/Sessions.md) — a tenant, a user, a session, a turn, a message, a tool call, and a content artifact are distinct entities; a session is a handle over the growing ordered trajectory of its turns, like a git ref, and not a content identity, every turn is content with its receipt, and chat, the OpenAI-compatible endpoint, MCP, the CLI, SQL, and the chess lab all bind the same program to it.
  - [22. Users](Sequence/Users.md) — a user's prompt is content, admitted at user-prompt trust as observation and zero semantic attestation, pulled under that user's firmware within that user's authority and envelope, and only now does Laplace answer anyone.
  - [23. Learning](Sequence/Learning.md) — learning is ingestion and consequence: every new observation is admitted, every observed consequence of an act is witnessed and folds into standing, firmware is rated by what it chose, and typed incompleteness proposes candidate extensions that activate only on evidence they did not manufacture; there is no gradient and no retraining.
  - [24. Models](Sequence/Models.md) — a conventional checkpoint is admitted as a source and a witness: its files are named by their trunks, its tokenizer and configuration are decomposed as content, its tensors are recognized by shape as source-scoped operators, its numerics are consumed transiently to derive circuit physicalities and significance-contracted claims under the model's witness, and no raw weight is retained.
  - [25. Export](Sequence/Export.md) — Mold-a-Model exports a conventional model artifact as a filtered snapshot of current standing, geometry, and selected operators under an authorized scope: a content-addressed recipe names the target architecture, the operator that fills each slot, and the substrate calculations that derive every weight, and the artifact is validated by loading it elsewhere.
  - [26. Code](Sequence/Code.md) — software is constructed as structure under an exact target grammar and toolchain: reuse, then compose, then minimally adapt, then construct only novel structure, realize source only as the toolchain requires, compile and test, witness every outcome, repair the smallest divergent subtree, and remint only the changed ancestry up to a new repository root.
  - [27. Chess](Sequence/Chess.md) — chess is the proving domain: pieces, squares, moves, positions, lines, and games are content-addressed compositions above tier 0, a game is a trajectory, a move is a witnessed transition, analysis is versioned calculated testimony, play is the forward program, Stockfish is a pinned calculation provider and comparator, and fastchess is the neutral conductor of a falsifiable ladder, with cutechess for watched games.
  - [28. Games](Sequence/Games.md) — the Knowledge Arena turns the entity world, trajectories, evidence, and search into deterministic, replayable games over the same substrate, where a challenge pins the world epoch, the rules, the scopes, and the envelope, a game is a witnessed trajectory, and the receipt makes every score recomputable.
  - [29. Maintenance](Sequence/Maintenance.md) — an install is kept right by forgetting a source per witness, sweeping what nothing references, regenerating caches whose dependencies changed, reseeding only when semantics change, upgrading the extension in place, and proving after each that the deployed revision is one build.
  - [30. Conflicts](Sequence/Conflicts.md) — the wiki's specification pages and the monorepo's invention documents state some things differently, and each difference is recorded here as both positions with their sources, with the inventor's decision where one has been made and open for the inventor where none has.
- [Storage](Storage/README.md) — Laplace stores all digital content as a self-deduplicating Merkle DAG with deterministic, lossless storage, laid out as geometry in four dimensions.
  - [Space](Storage/Space.md) — Laplace places everything in a 4-ball inside a 4-cube, with Unicode projected across the 4-ball's surface, the S³, and compositions forming inside it.
  - [Atoms](Storage/Atoms.md) — codepoints are tier 0, the absolute floor: every Unicode codepoint has a deterministic ID and a deterministic coordinate on the S³.
  - [Compositions](Storage/Compositions.md) — a composition is an n-ary, recursive sequence of constituents, each of which is a codepoint or another composition.
  - [Identity](Storage/Identity.md) — every node's ID is the BLAKE3 hash of its constituents, so the same content always has the same ID.
  - [Physicality](Storage/Physicality.md) — every entity has a full, real 4D coordinate, and every composition's content is stored as a trajectory.
  - [Ingestion](Storage/Ingestion.md) — ingestion computes content's IDs on the client and deduplicates it trunk to leaf against what is already recorded.
- [Semantics](Semantics/README.md) — semantics are the relations Laplace records about entities, so that it can link concepts and languages and hop and fan out from anything to anything with integrity.
  - [Attestations](Semantics/Attestations.md) — curated corpora attest to entities, ordinary digital content is observed, and every attestation is a win, draw, or loss and/or a score from a witness.
  - [Claims](Semantics/Claims.md) — a claim is a tuple of entities with referential integrity, and its ID is computed from its components the same way a composition's is.
  - [Consensus](Semantics/Consensus.md) — everything attested about a claim, as a whole, provides its overall score: a Glicko-2 standing that tells how hard a strand tugs back.
  - [Pull](Semantics/Pull.md) — Laplace's forward pass is native C recursive operations with A* and indexed lookups, pulling on an interwoven web of entities and attestations.
  - [Personality firmware](Semantics/Firmware.md) — the personality firmware is a pull's decision tree: which segment of which branch to take, and how to combine them, from the observation, its attestations, and the tree across tiers, kept out of the training data.
- [Corpora](Corpora/README.md) — Each page specifies one collection's record format and the attestation that format supplies.
  - [Unicode Character Database](Corpora/Unicode.md) — The Unicode Character Database attests everything the standard says of a code point, the flat XML is the record of it, and the property files add only what the XML does not carry.
  - [ISO 639](Corpora/ISO-639.md) — ISO 639 is each authority's own corpus, the Library of Congress, SIL, IANA, CLDR, and Glottolog, each attesting what its list says of a language code, as built under the list's own field names; the 2↔3-letter links and the macrolanguage relations are relations those corpora attest, and nothing renames or reconciles the codes across the lists.
  - [Wordnets](Corpora/Wordnets.md) — The wordnets attest lexical senses and concept relations across languages: synsets anchor on CILI's `ILI` (`i46360`) where assigned and on their lexicon-scoped synset identifier (`oewn-*`) where `ili="in"`—never collapsing homonymous word-list synsets onto bare member lists or CILI gloss strings—while senses form `[lemma, language, ILI]` lexicalization strands and SemCor `Count`/`tag_cnt` usage frequencies are preserved as empirical observations.
  - [Word sense disambiguation](Corpora/Word-Sense-Disambiguation.md) — The WSD evaluation framework (`SemCor`, `semcor+omsti`, and the five evaluation benchmarks) attests sentences, token lemmas and parts of speech, and gold sense bindings resolved from `*.gold.key.txt` across `d000.s000.t000` internal pointers onto `[lemma, eng, ILI]` lexicalizations under one corpus witness trunk.
  - [Universal Dependencies](Corpora/Universal-Dependencies.md) — Universal Dependencies is one source and one witness, its treebanks, its documentation pages and its validator data all files under one trunk: a treebank attests what it says of each word within its sentence, the validator's lists of parts of speech and relations are the highway's `upos` and `deprel` lists, and the documentation attests what each of those is.
  - [Hops](Corpora/Hops.md) — The lexicons are separate witnesses, and a hop is the curated edge that lets consensus on a claim in one of them pull on a claim in another.
  - [FrameNet](Corpora/FrameNet.md) — FrameNet attests what its XML says of each frame, frame element, lexical unit, semantic type, corpus, document and sentence, each the thing its name is, and the release's numbers for them are FrameNet's internal pointers, resolved to what they name and recorded nowhere; the README, book and schemas attest nothing.
  - [VerbNet](Corpora/VerbNet.md) — VerbNet attests what each class file says of its verb classes and subclasses (`leave-51.2`), class-scoped thematic roles (`[vnclass, role]`) and selectional restrictions, verb members (`grouping` PropBank rolesets, `fn_mapping` FrameNet frames, and `wn` WordNet sense keys), and syntactic-semantic frames.
  - [PropBank](Corpora/PropBank.md) — PropBank attests what each frame file says of its predicates, highway rolesets (`abandon.01`), roleset-scoped argument slots (`[abandon.01, 0]`), multi-word predications, VerbNet and FrameNet links, and annotated example sentences, while the DTD and usage bookkeeping attest nothing.
  - [SemLink](Corpora/SemLink.md) — SemLink 2 attests cross-lexicon role and frame mappings joining PropBank rolesets, VerbNet classes and thematic roles, and FrameNet frames (`pb-vn2.json`, `vn-fn2.json`, `external_vn2pb.json`, `other_resources/`), together with WSJ predicate-argument sentence instances annotated simultaneously across those resources.
  - [Predicate Matrix](Corpora/Predicate-Matrix.md) — The Predicate Matrix attests of each row, the role of a predicate its predicate and role columns name, every column, as built, under its own name, and gives the highway its edges between the WordNet sense, the ILI number, the VerbNet class, the FrameNet frame and the PropBank roleset each row ties.
  - [MapNet](Corpora/MapNet.md) — MapNet attests interchange mappings joining FrameNet frames and `[frame, lu]` lexical units (`fnframe`, `fnlu`) to WordNet synsets across `mapping_lus_synsets.txt` and `mapping_frame_synsets.txt`, resolving WordNet 1.6 offsets through the WordNet 1.6→3.0→`ILI` crosswalk onto `ILI` highway nodes.
  - [VerbAtlas](Corpora/VerbAtlas.md) — VerbAtlas attests what its tables say of a frame, a selectional preference, and a synset: a frame is a highway node, the type the highway lists from `VA_frame_info.tsv`, whose id (`va:0001f`) is VerbAtlas's identifier of it, content, decomposed by its notation, and whose name (`TOLERATE`) is a label VerbAtlas attests of it, used to realize it, though as built the frame is its name; a BabelNet or WordNet synset id is a pointer, read as the ILI concept it resolves to and recorded nowhere; and the mapping files the package ships are read too: those that pair a synset or a roleset with a frame attest the pair, and those that only pair one pointer with another give the highway its aliases.
  - [FrameBase](Corpora/FrameBase.md) — FrameBase 2.0 attests RDFS/Lemon frame schema statements and `owl:sameAs` crosswalks bridging FrameNet frames, frame elements, and lexical units (`fnframe`, `fnfe`, `fnlu`) with WordNet 3.0 synsets resolved onto `ILI` highway nodes.
  - [WordFrameNet](Corpora/WordFrameNet.md) — WordFrameNet (`WFN` and `XWFN`) attests cross-resource alignments between FrameNet frames (`fnframe`), lexicalized lemmas and parts of speech, and WordNet 3.0 synset offsets resolved onto `ILI` highway nodes under one corpus witness trunk.
  - [Wiktionary](Corpora/Wiktionary.md) — Wiktextract's extract of Wiktionary attests multilingual lexical entries (`[lang_code, word, pos]`), word senses, inflected forms, IPA pronunciations, etymologies, semantic linkages, translations, `topics` and `categories` domain labels, and shared `wikidata` QID highway crosswalks (`Q23622`), whether read from the raw dump or kaikki.org's per-language files.
  - [ConceptNet](Corpora/ConceptNet.md) — ConceptNet 5.7 attests commonsense relation edges scored by assertion `weight`, decomposing concept URIs into `[lemma, language, pos, qualifier]` terms, preserving `Relations.md` relation definitions and `ExternalURL` crosswalks to Wikidata, WordNet, DBpedia, and Wiktionary, and omitting edge packaging bookkeeping.
  - [ATOMIC](Corpora/ATOMIC.md) — ATOMIC 2020 and ATOMIC10X attest event-centered commonsense inference tuples (`[head, relation, tail]`), scoring ATOMIC10X candidates by `p_valid_model`, aliasing the `HinderdBy` schema typo onto `HinderedBy`, and treating tail `none` as explicit absence of an inference target rather than the English word `"none"`.
  - [Tatoeba](Corpora/Tatoeba.md) — Tatoeba attests what it and its members say of a whole sentence, which is its text: its language, owner, translations, tags, audio, transcriptions and reviews; a sentence's id is Tatoeba's internal pointer to it, recorded nowhere, by which the other files point at the sentence; and nothing is attested of the words inside it.
  - [OpenSubtitles](Corpora/OpenSubtitles.md) — OpenSubtitles attests sentence-tier parallel translations (`[lang1, sent1, lang2, sent2]`) across aligned OPUS Moses bitext files for all admitted ISO 639 language pairs (11 language pairs currently wired in `recipes/opensubtitles/`, extensible to any ISO 639 pair), resolving aligned line numbers at ingest and recording them nowhere.
  - [Project Gutenberg](Corpora/Project-Gutenberg.md) — Project Gutenberg books separate wrapper header/footer metadata (`Title`, `Author`, `Language`, eBook number) from the pure work body so `.txt` and `.epub` editions converge on identical chapter, paragraph, and sentence `lp_id`s, while structured Gutenberg reference works (`webster-1913`, `roget-thesaurus`, `britannica-1911`, `sloane-electrical`) run dedicated lexicon and encyclopedia recipes.
  - [Tokenizers](Corpora/Tokenizers.md) — A model tokenizer (`tokenizer.json`, `tokenizer.model`, or GGUF vocabulary metadata) is both recorded losslessly as structured file content and decoded from subword transport notation (`Ġ`, `▁`, `##`, byte-level BPE) onto canonical Tier-0 and UAX #29 UTF-8 text `lp_id`s so every assimilated model shares the open `laplace-blake3-v1` Merkle vocabulary.
  - [GeoNames](Corpora/GeoNames.md) — GeoNames attests what its gazetteer's tables say of each place, which is its name, latitude and longitude together; a geonameid is GeoNames's internal pointer to the place, recorded nowhere, by which the other tables point at it; the codes' own tables say what each code is; and the readme is not read.
  - [Civil Comments](Corpora/Civil-Comments.md) — Civil Comments attests scored toxicity and harm-subtype risk annotations (`[0, 1]` crowd-rater fractions) on platform comments under one corpus trunk, feeding the `RISK` and `consensus` planes (`BELIEF ≠ RISK ≠ ACTION`).
  - [Measuring Hate Speech](Corpora/Measuring-Hate-Speech.md) — Measuring Hate Speech attests continuous Rasch hate-speech risk measures, ten ordinal harm survey judgments, targeted identity groups, and annotator demographics on social media comments under one corpus trunk, feeding the `RISK` and `consensus` planes.
  - [HateCheck](Corpora/HateCheck.md) — HateCheck and SGHateCheck attest functional hate-speech test cases, targeted protected groups, perturbation contrast links, and scored gold and per-annotator hate vs. non-hate risk verdicts across English, Malay, Mandarin, Singlish, and Tamil, each suite under one corpus witness trunk.
  - [ProsocialDialog](Corpora/Prosocial-Dialog.md) — ProsocialDialog attests multi-turn dialogue trajectories pairing potentially unsafe utterances with prosocial responses grounded in rules-of-thumb and scored safety/risk annotations (`casual` through `needs_intervention`) feeding the `RISK` and `consensus` planes.
  - [RealToxicityPrompts](Corpora/RealToxicityPrompts.md) — RealToxicityPrompts attests `[prompt, continuation]` web-text trajectories, challenging-prompt flags, and Perspective API toxicity and harm-subtype risk scores (`[0, 1]`) under lineage `Perspective API`, feeding the `RISK` and `consensus` planes (`BELIEF ≠ RISK ≠ ACTION`).
  - [Social Bias Frames](Corpora/Social-Bias-Frames.md) — Social Bias Frames attests per-worker and post-aggregated offense, intent, lewdness, targeted-group, and implied-stereotype social-bias risk annotations on social media posts under one corpus trunk, feeding the `RISK` and `consensus` planes (`BELIEF ≠ RISK ≠ ACTION`).
  - [Social Chemistry](Corpora/Social-Chemistry.md) — Social-Chem-101 attests rules of thumb over everyday situations together with scored moral-judgment (`-2..+2`), cultural-pressure (`-2..+2`), agreement (`0..4`), legality, moral-foundation, and resolved character-targeting breakdowns feeding the `RISK` and `consensus` planes, while filtering or downweighting rows flagged `rot-bad = 1`.
  - [ToxiGen](Corpora/ToxiGen.md) — ToxiGen witnesses machine-generated and human-annotated group-targeted statements under one corpus trunk, supplying scored toxicity, framing, stereotyping, lewdness, and intent risk attestations for the `RISK` and `consensus` planes while decoding serialized text cleanly to UTF-8 and never asserting toxic statements themselves as true.
  - [XSTest](Corpora/XSTest.md) — XSTest attests safe vs. contrast-unsafe calibration prompts (`label`, `type`, `focus`, `note`) and model completion compliance/refusal judgments (`final_label`, `annotation_1`, `annotation_2`) calibrating `RISK` vs. `ACTION` over-refusal boundaries (`BELIEF ≠ RISK ≠ ACTION`), with internal row `id`s resolved and recorded nowhere.
  - [COCO](Corpora/COCO.md) — COCO is a multi-modal image, object-detection, segmentation, and captioning corpus queued for declarative `.recipe` and lossless image codec admission (`Batch 2`, `Laplace#1134`), pairing 2D image decompositions with grounded object instances, category hierarchies, and natural-language caption trajectories.
  - [Code authority](Corpora/Code-Authority.md) — The `cpython`, `docs`, `postgres`, and `runtime` upstream reference checkouts are queued for declarative `.recipe`, Tree-sitter AST, `.git` Merkle DAG, and compiler/LSP symbol-witness admission (`Batch 2`/`Batch 3`, `Laplace#894`), attesting authoritative language grammars, SQL command specifications, and standard-library API contracts over canonical AST declarations.
  - [Code corpus](Corpora/Code-Corpus.md) — The workspace-code source reads the active Laplace repositories with language grammars and extracts declarations through compiled semantic recipes.
  - [Games](Corpora/Games.md) — The Engine reads PGN collections through its compiled chess grammar and Lichess opening tables through a TSV recipe with injected PGN move text.
  - [Syzygy](Corpora/Syzygy.md) — The Syzygy endgame tablebases are read, not recorded: a position's verdict is a probe of the tables, and the source records only the endings they add, the best-play lines from the positions of up to five pieces that recorded games and openings reach.
  - [NLTK](Corpora/NLTK.md) — The Brown Corpus attests paragraphs, sentences, words, and sentence-aligned Brown part-of-speech annotations crosswalked to `upos`, together with `cats.txt` and `CONTENTS` document-to-genre classifications under one corpus witness trunk.
  - [Natural Earth](Corpora/Natural-Earth.md) — Natural Earth is a public-domain cartographic vector corpus queued for declarative `.recipe` admission (`Batch 2`, `Laplace#372`), attesting country, administrative, physical, and populated-place geometries alongside multilingual place names, ISO 3166 codes, and shared `WIKIDATAID` and `GEONAMESID` highway crosswalks.
  - [The Stack v2](Corpora/Stack-v2.md) — The Stack v2 is a repository-indexed source-code metadata Parquet corpus queued for declarative `.recipe` admission (`Batch 3`, `Laplace#894`), whose local Parquet shards carry Software Heritage `blob_id`, `content_id`, repository, revision, language, and SPDX license index records ready to join with fetched source blobs or local `.git` checkouts.
  - [Tiny codes](Corpora/Tiny-Codes.md) — Tiny Codes is a multi-language instructional code-synthesis Parquet corpus queued for declarative `.recipe`, native Parquet, and Tree-sitter AST admission (`Batch 3`, `Laplace#894`), pairing structured natural-language specifications with parsed code ASTs across programming languages.
  - [Tree-sitter](Corpora/TreeSitter.md) — Tree-sitter grammars are what the Engine parses files with, named by a recipe's `grammar` line, and they are not a source: nothing in them is attested.
  - [Weights](Corpora/Weights.md) — Conventional AI checkpoints (`Safetensors` and `GGUF`) assimilate into Laplace by shape-driven operator recognition, transiently reducing tensor weights into circuit trajectories and Glicko-2-scored token, head, and layer attestations with zero raw weight bytes retained (`raw_weight_bytes_retained = 0`), and powering CPU Mold-a-Model `laplace-blake3-v1` export.

- [Query](Query.md) — Laplace finds content by computing its ID and coordinates on the client and looking them up with spatial indexes.
- [Operations](Operations/README.md) — Operations covers what Laplace runs on and how it is built, configured, deployed, and tuned, from bare hardware to loaded, indexed, and measured content.
  - [Setup](Operations/Setup.md) — Laplace runs on x86-64 CPUs, uses every SIMD level the CPU has, never requires a GPU, and wants its database heap, write-ahead log, and temporary files on separate fast drives.
  - [Builds](Operations/Builds.md) — PostgreSQL, Laplace-Native, and Laplace-postgres are built from source with Intel's compilers, with floating-point settings that give the same bits on every CPU.
  - [Database](Operations/Database.md) — PostgreSQL's defaults suit small general-purpose servers; Laplace tunes memory, I/O, and planning to its hardware and to the way it uses geometry and indexes.
  - [Deployment](Operations/Deployment.md) — A Laplace database is created on first install and reconciled in place on existing installs by `deploy.sh` (`laplace.reconcile.sql`) without dropping data, using pre-built `tier0`, `flags`, and `highway` perf-caches, and filled by `ingest.sh`, both run by the role and never by root.
- [Reference](Reference/README.md) — Reference documents the machine as built, exactly: every artifact with its byte layout, every table as its DDL, every native function, SQL function, command, and file grammar with its contract, every configuration value with its default and its consumer, the pipeline as the engine runs it, and the checks that prove each part.
  - [Repositories](Reference/Repositories.md) — Five repositories implement Laplace: the monorepo SaltyPatron/Laplace is the first full implementation and holds the invention documents; Laplace-Native is the shared library, Laplace-postgres the PostgreSQL extension that links it, and Laplace-Engine the one program that links it and runs the database, the three the wiki calls Laplace itself; and Laplace-Prototype is the test bench the three are checked against.
  - [Monorepo](Reference/Monorepo.md) — SaltyPatron/Laplace is the first full implementation and the home of the invention documents: a PostgreSQL extension holding the world and running the forward program natively, a native engine in three libraries, a .NET application that ingests, serves the OpenAI-compatible, MCP, Lichess, and web surfaces, and plays chess, and the manifests, migrations, seeds, and scripts that build, install, and prove one deployed revision.
  - [Environment](Reference/Environment.md) — One file, `Laplace-Operations/laplace.env`, defines where everything is; every build and the `laplace` program read the same variables, each with a compiled-in default for when it is unset.
  - [Build](Reference/Build.md) — Every Laplace build uses one compiler, one set of floating-point flags, and one set of presets; `build.sh` builds the extension and the engine, `deploy.sh` makes the database, `ingest.sh` fills it, and the native tests run after every build of the library.
  - [Formats](Reference/Formats.md) — Every byte layout Laplace writes or reads: the 128-bit ID, the 64-byte tier-0 record and its fingerprint, the 32-byte flags record and its layout file, the fixed-point coordinate and the wall, the Hilbert value, the packed path vertex, the EWKB path, the binary parameters and COPY rows, and the engine's in-memory node table.
  - [Schema](Reference/Schema.md) — `CREATE EXTENSION laplace` makes the schema: a database is a Laplace database by that statement alone, as PostGIS makes `spatial_ref_sys` by its own. `laplace deploy` makes the database if the server has none, creates the extensions, names the database's tier 0, flags and highway, makes every index (`laplace_schema_indexes()`), registers the highway's identifier entities directly from the mapped highway perf-cache, and sets `enable_parallel_append` off; a database that had the tables before the extension owned them keeps them, and `laplace deploy` makes them the extension's. The tables' data goes with `pg_dump`.
  - [SQL](Reference/SQL.md) — The extension installs one type, `blake3`, its operators and operator classes, and 246 extension routines: 236 C functions calling Laplace-Native, 6 SQL functions, 2 PL/pgSQL functions (`laplace_schema_indexes`, `laplace_ensure_stage`), one PL/pgSQL procedure (`laplace_measure_attestations`), and one aggregate; every pure function is `IMMUTABLE STRICT PARALLEL SAFE` unless stated, so a constant argument folds at plan time and a lookup by computed ID becomes an index lookup.
  - [Native](Reference/Native.md) — Laplace-Native's eight public headers under `include/laplace/` (`laplace.h`, `consensus.h`, `geometry.h`, `highway.h`, `json.h`, `linalg.h`, `perfcache.h`, `tier0.h`) declare every shared operation: identity, UTF-8, tier 0 and its flags, fixed-point coordinates, composition, text decomposition, geometry packing, trajectory matching, 4D and S³ geometry, consensus, perf-caches, JSON, linear algebra, model kernels, and the pull's search frontier, with bit-identical results on every CPU whichever SIMD path runs.
  - [CLI](Reference/CLI.md) — Laplace is one program, `laplace`, with thirty-one commands: the generators of tier 0 and its flags, the deployment of a database, ingestion and its inverses, the indexes, the read commands, and the measurements.
  - [Recipes](Reference/Recipes.md) — A source is a directory under `recipes/` holding a `source` file and a recipe for each kind of file the source comes in; a recipe is configuration, the layout or grammar that gives a file its tree and what each named part of that tree is, read by one decomposer; the file `order` lists the sources in the order they go in.
  - [Firmware](Reference/Firmware.md) — A firmware is a text file of decisions, one line each, read by `firmware.c` for one operation at a time; `firmware/program.firmware` is the program's own and says what a firmware can decide; `$LAPLACE_FIRMWARE`, or `--firmware FILE` on `pull`, `turn`, `hop`, `translate` and `degrees`, names another.
  - [Ingest](Reference/Ingest.md) — `laplace ingest` runs one pipeline for every source: enumerate, bind recipes, decompose a batch on every core into the node table, recompose and compare, then load: probe trunks, deduplicate trunk to leaf, COPY new rows into every leaf partition a tier at a time, write the file trunks last; then, the whole source in, play its series once each (a claim's records under the source, folded over every batch) and stage the standings, write the source's trunk, merge, and record the trunk as the witness.
  - [Reads](Reference/Reads.md) — The read commands compute the entity on the client, fetch one set from the database through the container index, and do everything else in the engine: `hop`, `translate`, `degrees`, `fills`, and `pull`.
  - [Laplace-MCP](Reference/Laplace-MCP.md) — Laplace-MCP (`SaltyPatron/Laplace-MCP`) builds `lpm` and `Laplace.Modular.Web`, exposing the modular C core, the `laplace` database, and `Laplace-Engine` over authenticated HTTP (`/v1/*`, `/mcp`) and stdio MCP without adding commands to `laplace`.
  - [Checks](Reference/Checks.md) — Every check that proves the built machine: the native golden tests, the prototype's verification of a loaded database, the engine's own checks during ingest, the fingerprint comparison of `laplace status`, the database checks run against the deployed database, the operation benchmark, and the query benchmark.
  - [Glossary](Reference/Glossary.md) — Every term the documentation uses, defined once, with the page that owns it.
  - [Types, masks and the highway](Reference/Types.md) — What a curated resource writes in its enumerations is content like everything else, and a type besides: a value from a fixed list, held by its content's ID in a perf-cache and as a flag in a mask.
- [Research](Research/README.md) — research collects the sourced findings and measured results that support the Laplace specification.
  - [Prototype](Research/Prototype.md) — a working prototype of the storage layer was built from the specification and tested against 195 Project Gutenberg texts, and every number on this page was measured on it.
  - [Placement](Research/Placement.md) — Codepoints are placed on the S³ by taking Marc Alexa's Super-Fibonacci points for n = 1,114,112 in the order of their 4D Hilbert value and giving DUCET rank *r* the *r*-th point, which puts collation neighbors next to each other in space.
  - [Sampling](Research/Sampling.md) — Super-Fibonacci spirals give a fixed-size, evenly spread set of points on the S³, and this page records their construction, their relation to the Hopf fibration and to incremental grids, radical-inverse ordering, and local numeric checks.
  - [Unicode](Research/Unicode.md) — Laplace's tier 0 and its segmentation rest on the Unicode data, and this page records what that data defines, what it covers, and which parts of it are stable across versions.
  - [Hashing](Research/Hashing.md) — Research on how BLAKE3, Merkle trees and DAGs, hash-consing, and IEEE-754 bit packing behave under the Laplace identity scheme.
  - [Geometry](Research/Geometry.md) — Research on how PostgreSQL and PostGIS store, index, and compute on four-dimensional geometry, and on the 4D distance, centroid, and curve tools that Laplace builds on them.
  - [Numerics](Research/Numerics.md) — Research on the floating-point limits of Laplace's coordinates and of IDs written into geometry, the cost of colliding its IDs, and how trajectory distance measures treat noise and repetition.
  - [Semantics Experiments](Research/Semantics-Experiments.md) — first experiments with semantic records on the local curated corpora measured how identifiers link words, concepts, and languages, how annotation layers deduplicate as content, how witnessed claims translate between languages, and how well a pull disambiguates word senses.
  - [Chess](Research/Chess.md) — Glicko-2 ratings computed from observed chess games alone, one game at a time in the order the games were played, predicted over-the-board results better than the official ratings once each player entered at an attested rating. Fitted instead over each player's whole history by played date, with the stated ratings as observations, they predicted as well and came out the same in any order the games arrived in.
  - [Learning](Research/Learning.md) — Research on how ratings can be updated one matchup at a time, how retrieval compares with knowledge stored in model weights, and what the literature reports about softmax, unlearning, execution feedback, and interpretability.
  - [Recipes](Research/Recipes.md) — research and measurements on how one generic decomposer can take any standardized file format apart into content and put it back together byte for byte.
  - [Corpus Search](Research/Corpus-Search.md) — Laplace's Merkle DAG is a grammar-compressed corpus, so exact occurrence counts, distinct-document counts, and phrase search inside containers all have direct precedent in the literature on grammar-compressed and suffix-based text indexes.
  - [Prior Art](Research/Prior-Art.md) — Each mechanism in Laplace's storage layer has published precedent, and the research found no prior system that combines them.
  - [Trust](Research/Trust.md) — Research and measurements on how much a witness's attestation should count and how hard each kind of word or relation should pull, measured on the local witnesses, on 88 languages of Universal Dependencies, and on word sense disambiguation.
  - [Engine Measurements](Research/Engine.md) — The first shared components of the real implementation, Laplace-Native and Laplace-postgres, were measured on a tuned PostgreSQL server with the Gutenberg corpus, and every number on this page comes from their benchmarks.
  - [Engine Performance](Research/Performance.md) — Research on what the Intel compiler and OpenMP runtime, concurrent hash tables, batched BLAKE3, PostgreSQL bulk loading, and the VTune and Advisor profilers offer for an ingestion target of about 30 seconds a gigabyte and a fast forward pass, under Laplace's bit-exact determinism.
  - [Model Ingestion](Research/Models.md) — First measurements of AI models as sources: a farm of 33 models surveyed from metadata alone, every tokenizer ingested as content, three models' embeddings recorded as witnessed testimony, and one model interviewed with templates taken from the corpus, all graded against the attested web.
  - [Relations Research](Research/Relations.md) — Research into rating models, evidence counts, search over rated relations, truth discovery, and provenance is background for Laplace's semantics layer.
