# Monorepo

SaltyPatron/Laplace is the first full implementation and the home of the invention documents: a PostgreSQL extension holding the world and running the forward program natively, a native engine in three libraries, a .NET application that ingests, serves the OpenAI-compatible, MCP, Lichess, and web surfaces, and plays chess, and the manifests, migrations, seeds, and scripts that build, install, and prove one deployed revision.

The invention is `docs/INVENTION.md`, `docs/INVENTIONS.md`, `docs/CAPABILITIES.md`, and the binding specs 05, 06, 08, 09, 11, 33, 34, 36, 37, 38, 39; the monorepo's `AGENTS.md` says code implements those documents and a lower document never defines a smaller machine. `docs/ARCHITECTURE.md` says how the repository implements them and `docs/OPERATING_SEQUENCE.md` walks it end to end. This page records what is built there, by name, so the Sequence can say which of its operations the monorepo performs and how its laws differ from the split repositories'. Everything here is from the monorepo's sources at its current head, merge of pull request 1727; where a claim rests on a document rather than on code the wiki read, the page says so.

## Build and install

`scripts/pipeline.sh` sequences the phases `clean codegen build build-native build-extension-sql build-app build-web install install-extension-sql install-ingest-runtime activate-postgres migrate sync-extension tune-pg tune-laplace perfcache-guc api-env publish foundation test`; `Justfile` wraps them for a developer, and `.github/workflows/laplace.yml` runs them as "Plan affected product work" then "Build, deploy, and read back affected product". `scripts/setup-host.sh` and `setup-storage.sh` lay out the host:

| Purpose | Place |
| --- | --- |
| installed runtime | `/opt/laplace` |
| PostgreSQL 18, built by `scripts/postgresql-release.py` | `/opt/laplace/pgsql-18` |
| PostgreSQL data | `/opt/laplace/pgdata` |
| write-ahead log | `/var/lib/pgwal` |
| spill | `/pgtemp` |
| build and tool scratch | `/build` |
| the admitted source estate | `/vault`, `LAPLACE_DATA_ROOT` `/vault/Data` |

The native engine compiles under `icx` with `-fp-model=precise -fimf-arch-consistency=true -no-fma`, under gcc or clang with `-fno-fast-math -ffp-contract=off`, C17 and C++20, one instruction set per build: `LAPLACE_TARGET_ISA` AVX2 (`-march=haswell`) or AVX512 (`-march=sapphirerapids`), with MKL's conditional bitwise reproducibility set to match. There is no run-time dispatch. The build produces `liblaplace_core`, `liblaplace_dynamics`, `liblaplace_synthesis`, the extensions `laplace_geom.so` and `laplace_substrate.so`, the .NET solution `app/Laplace.slnx` (twelve projects and nine test projects), and the Vite web under `web/`.

One deployed revision is proved by `scripts/check-deployed-revision.sh`: the `.laplace-source-revision` receipts of the application payload and of the native prefix must name the checkout's commit, `liblaplace_core.so.0.1.0` must have the same SHA-256 in both, and `laplace_execution_module.txt` must name an installed `laplace_execution_<16 hex>.so`. The execution module carries the SQL bindings' C functions under a hash of the build, so a new build is selected by the catalog while the server keeps running (`execution_module.c`, `pipeline.sh sync-extension`).

## Tier 0 and the perfcaches

`laplace_t0_perfcache.bin` is generated from `ucd.all.flat.xml` and `allkeys.txt` by `laplace_unicode_seed_compute` (`unicode_seed.cpp`) through the CMake target `laplace_t0_perfcache`, and compared at build with `laplace_t0_perfcache.reference.bin`. Its format is `perfcache_format.h`, the blob law of spec 33:

| Part | Layout |
| --- | --- |
| header, 128 bytes | `magic` `0x4652504C` (`LPRF`), `format_version` 4, `ucd_version[8]`, `uca_version[8]`, record count and size and offset, decomposition record and data counts and offsets, composition record count and offset, `ucd_hash` 16 bytes, 16 reserved |
| record, 80 bytes, 1,114,112 of them | `codepoint` u32, `uca_order` u32, `coord[4]` doubles, `hilbert` 16 bytes, `hash` 16 bytes, `flags` u32 (`GB` 4 bits, `WB` 5, `SB` 4, `InCB` 2, `ccc` 8, `White_Space` 1), pad |
| decomposition and composition tables | `(cp, start, length)` into a codepoint array; `(first, second, composed)` |
| trailer, 16 bytes | the checksum `codepoint_table_load_perfcache` verifies and `codepoint_table_copy_receipt` returns |

The loader rejects any other version, record count, or trailer. `identity.perfcache_receipt()` reports the receipt from inside the database. Beside it: `laplace_highway_perfcache.bin` generated from `relation_types.toml`, the vocabulary perfcache from `engine/manifest/vocabulary/`, the number ROM of `modality_number_table` (the roots 0 to 255), and the chess position and transition perfcaches exported from recorded games by `export-qualified-chess-floors.py`. Four settings name them, `laplace_substrate.perfcache_path`, `highway_perfcache_path`, `vocabulary_perfcache_path`, `chess_position_perfcache_path`, set with `ALTER SYSTEM` by `pipeline.sh perfcache-guc`. Codegen rewrites a blob only when its bytes change, because a mapped file cannot be truncated under a live ingest.

## Identity, placement, and the carrier

- **Identity** (`hash128.c`): `hash128_merkle` is BLAKE3-128 over a domain byte `0x01` and the ordered child ids; one child is that child; the `tier` argument is discarded. A codepoint's id is BLAKE3-128 of its UTF-8. Because of the domain byte, a composition's id here differs from its id in the split repositories, which hash the child ids alone, and so it differs for every composition there is. The domain byte violates the identity law, and `docs/ARCHITECTURE.md` documents it wrongly: a composition's ID is BLAKE3 over its children's 16-byte IDs in order and nothing else, which is what Laplace-Native and the Engine compute; a node cannot collide with a leaf without it, because a leaf hashes one to four bytes of UTF-8 and a node at least 32.
- **Made-up ids** (`Hash128.cs`, `SubstrateCanonicalIds.cs`, `readback/canonical_id.sql.in`, `identity/source_id.sql.in`): `Hash128.OfCanonical(string)` is BLAKE3-128 of a string's UTF-8 bytes taken as one blob, and `SubstrateCanonicalIds` builds such strings from invented paths (`Source(name)`, `ConversationSession(tenant, key)`, `Of(...)`, `OfVersioned(...)`, a `/v1` suffix); the SQL `realize.canonical_id(text)` does the same, and `laplace.source_id(name)` is `canonical_id('substrate/source/' || name || '/v1')`. They are called from some 66 C# files outside the tests and from the chess, converse, identity and ops SQL families. Each is a fake identifier: a blob hash gives a text a second ID beside its content ID, and a made-up path names nothing that was ever content. The law requires the string to be a decomposed entity, a trunk that is referenced, or an attestation that is recorded, and no version suffix in any ID.
- **Placement** (`super_fibonacci.c`): rank *r* in DUCET order takes `super_fibonacci_point_open(r)`, whose radial parameter is the base-2 radical inverse of *r*, so admitting more atoms moves none already placed. The Sequence follows the wiki's H1 placement, rank *r* to the *r*-th Hilbert-ordered point of the fixed set; the two are [30. Conflicts](../Sequence/Conflicts.md) P1. Coordinates are doubles; there is no fixed-point grid and no wall nudge at tier 0.
- **Hilbert** (`hilbert4d.c`): 32 bits per axis into a 128-bit value, `hilbert4d_encode`, stored as 16-byte `hilbert_index`; the split repositories use 16 bits per axis into 64.
- **Coordinate of a composition** (`math4d.c`): `math4d_centroid` in doubles; `math4d_karcher_mean` exists and the managed chess and model paths use it, [30. Conflicts](../Sequence/Conflicts.md) P3.
- **The carrier** (`mantissa.c`, `trajectory.c`): a GeometryZM vertex carries 212 bits, `entity_id` 128, `ordinal` 16, `run_length` 16, `flags` 52. The flags hold a five-bit tier and a vertex class: ordinary content; atom, with a 21-bit codepoint; testimony, with a score; factor, six float32 values per vertex for a circuit's factor matrix; parse, with UPOS, dependency relation, head ordinal, and subtype codes. Ordinal and run beyond 16 bits are carried by run splitting. The split repositories pack 43 + 43 + 42 bits of id into X, Y, Z and the run and kind into M; that is [30. Conflicts](../Sequence/Conflicts.md) P2.
- **The realized curve** (`sql/functions/structural/entity_curve.sql.in`): each vertex unpacked, the child's physicality resolved, its coordinate read, ordered by ordinal; shape measures run on that, never on the carrier.

## Ingest

`scripts/ingest-source.sh <source>` runs `Laplace.Cli ingest` from the installed runtime under `/opt/laplace/ingest/current`, with the sources in three groups: `FLOOR` (`unicode`, `uca`, `iso639`, `operational`, `cili`), `KNOWLEDGE` (`wordnet`, `oewn`, `omw`, `verbnet`, `verbnet-gl`, `propbank`, `framenet`, `mapnet`, `wordframenet`, `semlink`, `conceptnet`, `atomic2020`, `ud`, `wiktionary`), `USAGE` (`tatoeba`, `opensubtitles`), and the lanes `document`, `code`, `repo`, `stack`, `tiny-codes`, `tabular`, `recipe`, `agents`, `chess` and its corpora, `safetensors`. A source is a decomposer in `Laplace.Decomposers` (31, and 13 in `Laplace.Chess`) declaring `SourceId`, `SourceName`, `TrustClass`, `Relations`, `License`, `Profile`, and a recipe under `recipes/<source>/<release>/` (`*.source.json`, `*.recipe.json`; `docs/invention/recipe-schema.md`), compiled by `NativeRecipeCompiler` and `SemanticSourceRecipe`. `SourceId` is the made-up id of the source's name (`substrate/source/<name>/v1`, above), which the law forbids: the witness is the source trunk, `[source record, its files' trunks]`, with the source's name content inside its source record, never a blob hash of a name. The `operational` source admits the invention documents themselves under `SubstrateMandate` (`seeds/operational/README.md`).

The pipeline (`IngestPipeline.cs`, `docs/ARCHITECTURE.md` §5): every artifact opened lazily in the worker that claims it; a source trunk entity above file trunk entities; extraction into staged compositions, claims, and trunks; novelty proved trunk-first against the substrate through the bitmap probes and `merkle_dedup`; physicalities realized for novel entities only; entities, physicalities, and attestations landed leaf to trunk by binary COPY, `partition_route` computing each row's hash partition natively so every backend is handed whole leaves; then one Glicko-2 scoring of the landed evidence into consensus, once per source. `staged_load.cpp` merges staged claims by attestation id, games and score sums added, qualifier masks OR-ed, and scores each touched cell over all of its evidence. The journals record every run (`ingest_run_journal`: status, phase, units, entities, physicalities, attestations, fold and writer times, throughput against a baseline), every file (`ingest_file_journal`: `resume_fingerprint` BLAKE3 of the bytes, `disposition` admitted, equivalent-packaging, superseded, excluded-with-reason, unsupported-with-why-not, absent), every flushed working set, and completion per unit and per layer. `ops.ingest_runs`, `ops.ingest_files`, `ops.ingest_completion`, `ops.source_status`, and `ops.evict_source` read and undo it.

## Consensus

`glicko2.c` is Glicko-2 in fixed point, ×10⁹: `glicko2_fold_grouped_period` folds one rating period per cell over all of its evidence grouped by identical opponent, τ 0.5, the volatility by the Illinois method to 2 × 10⁻⁵; `glicko2_decay_rd_in_place` widens the deviation with elapsed time over a 30-day rating period; `laplace_effective_mu_fp` is `rating − 2·rd` and `laplace_glicko2_refuted` is that below 1500. A witness of weight *w* in [0, 1], its trust class's prior, plays at opponent deviation `350 + (30 − 350)·w` and opponent rating `1500 + 320·(2w − 1)` (`attestation_engine.c`); an attestation's id is over subject, type, object, source, and context, its source the made-up `source_id`. `consensus_bulk_write.c`, `fold.consensus_upsert`, and the app's `ConsensusAccumulatingWriter` write standings and deposit highway masks; `ops.refold_source` and `ConsensusPipelinedRefold.cs` refold touched cells after an eviction. The split repositories play one matchup per attestation as it arrives with no rating period, never widen for time, and turn trust into the opponent's deviation by `g(φ) = |t|`; those differences are [30. Conflicts](../Sequence/Conflicts.md) T3 and the entry of [13. Consensus](../Sequence/Consensus.md).

## Firmware and the forward program

`firmware.toml` declares the image `default`, class `personality`, version 1: `salience_floor` 0.3, `semantic_hops` 2, `fanout` 8, `meeting_hops` 2, `meeting_fanout` 256, `meeting_frontier` 4096, `sharing_window` 32, `sharing_cap` 4096, `spread` 0.6, `top_k` 10, `steps` 128, `max_stride` 5; codegen gives it a content id; `pg_laplace_firmware` reads it.

`generation.forward_program(p_prompt …, p_seed, p_hops = 2, p_fanout = 8, p_prior_frontier, p_output_relation_types)` is one C entry, `pg_laplace_forward_trace`, over RESOLVE, COUPLE, ORIENT, ROUTE, SCAN, COMPOSE, PROPOSE, STEER, SELECT, REALIZE, WITNESS. `converse.respond` (`forward_respond.c`) is COUPLE: every term of the observation expands at once from its own key and the keys its binding relations name, an indexed star of consensus neighbours per hop under hops, fanout, and a frontier cap, each route kept typed per term (relation, hops, predecessor, rating, deviation, volatility, witnesses, minimum salience, minimum conservative standing), candidates ordered by terms covered, minimum salience, fewest hops, minimum standing, and routes returned per term, never folded into one score. `cognition_program.h` compiles the observation into obligations from its occurrence ordinals and mints a `program_id` over the coupling, a `semantic_act_id` over program and output, and a disposition: open, complete, exhausted, budget-exhausted, ambiguous; an ambiguous program finalizes and emits nothing. `steer_candidates.c`, `prompt_intent.h`, and `intent_stage` steer and stage; `generation.forward_text` realizes a completed act and never an exhausted frontier; `converse.forward_turn` passes prior turns as discourse identities; `converse.chat(prompt, session, lang, shape, bands, topic, …)` is the chat surface, its connectives from `converse.chat_scaffold`. `task_shape.c` and `converse.query_shapes` read the declared relation-read shapes seeded under `seeds/operational/tasks/`. `docs/read-path.md` §11 lists the open obligations: complete typed coupling coverage, the remaining row-at-a-time paths, the centroid against Karcher, and the preflight-against-actual receipts.

## Surfaces, sessions, authority, and the envelope

`Laplace.Endpoints.OpenAICompat` serves `/v1/chat/completions`, `/v1/completions`, `/v1/embeddings`, `/v1/models`, `/v1/query`, `/v1/op` (an installed operation by name from the `ops.api` allow-list), `/v1/explore/*` (browse, entities, containers, graph, neighbors, mesh, taxonomy, matchup, decompose, storage-proof, the Unicode cloud), `/v1/content/text` and `/v1/content/code`, `/v1/evidence/{target}`, `/v1/feedback`, `/v1/synthesis/export`, `/v1/analyze/machine-cost`, `/v1/recipe/compile`, `/v1/admin/ingest/*`, `/v1/account/*`, `/v1/auth/*`, `/v1/billing/*`, `/chess/*`, and health; `Laplace.Endpoints.Mcp` the same operations as MCP tools; `Laplace.Endpoints.Lichess` the Lichess bot; `Laplace.Cli` the ingest, query, decomposition, eval, evict, foundry, cookbook, and chess commands; `web/` the chat, explore, query, forward-proof, chess, billing, and admin views.

A session is a Projection physicality, type 3, over its turn ids in order, rewritten on each append (`conversation_session.c`, `converse.session_turns`); `TurnWitness` makes the tenant the source identity and the session the context of every attestation a turn writes, per spec 34, the session's id `SubstrateCanonicalIds.ConversationSession(tenant, key)`, a made-up id. Both violate the law: a tenant is authorization and isolation, not a witness and not trust; the user is the witness; a session is a handle, a projection over the growing ordered trajectory of its turns, like a git ref, and not a hashed identity; a turn is one act whose session and ordinal are position, never part of an ID; a message is a content trunk. A principal is a tenant resolved by `TenantResolution` in header, key, or identity mode, with API keys, browser identity, workspaces, and invitations, and the database roles `laplace_admin`, `laplace_app`, `laplace_readonly`; `docs/guides/knowledge-authority.md` and `shared-workspace-controls.md` state the rules. The envelope is billed: `/v1/billing/preflight` and the quote endpoints, `QuoteGate.RequireQuoteAsync` before an execution, `BillingReceipt` after, `/v1/billing/entitlements/consume`; hops and fanout are the parameters of the forward program; the receipt is `LaplaceCognitionProgramReceipt`.
